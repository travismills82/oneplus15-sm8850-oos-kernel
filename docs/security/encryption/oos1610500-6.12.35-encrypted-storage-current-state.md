## Current encrypted-storage implementation

| Layer | Source | Build ownership | Current role |
|---|---|---|---|
| F2FS | `kernel_platform/common/fs/f2fs/` | built-in common kernel | `/data` filesystem, encryption I/O integration, compression and security xattrs |
| fscrypt | `kernel_platform/common/fs/crypto/` | built-in common kernel | v2 policy handling, master/per-mode keys, inlinecrypt selection and key lifetime |
| blk-crypto | `kernel_platform/common/block/blk-crypto*.c` | built-in common kernel | bio crypto contexts, profiles, keyslots, DUN and fallback handling |
| device mapper | `kernel_platform/common/drivers/md/dm*.c` | built-in common kernel | metadata-encryption mapping and wrapped-key operation forwarding |
| UFS core crypto | `kernel_platform/common/drivers/ufs/core/ufshcd-crypto.c` | built-in common kernel | common UFS crypto-profile and request descriptor integration |
| QTI UFS crypto | `kernel_platform/soc-repo/drivers/ufs/host/ufshcd-crypto-qti.c` | `ufshcd-crypto-qti.ko` | hardware-wrapped-key profile, key program/evict and software-secret derivation |
| Qualcomm UFS host | `kernel_platform/soc-repo/drivers/ufs/host/ufs-qcom.c` | `ufs-qcom.ko` | Canoe UFS controller, reset, power and vendor integration |
| Qualcomm ICE | `kernel_platform/soc-repo/drivers/soc/qcom/ice.c` | `qcom_ice.ko` | HWKM, ICE keyslot programming/eviction and wrapped-key handling |
| Qualcomm SCM | `kernel_platform/soc-repo/drivers/firmware/qcom/qcom_scm*.c` | `qcom-scm.ko` | secure-world ICE key calls and shared-memory bridge |
| Secure world | firmware outside this repository | immutable firmware | unwraps/programs hardware-wrapped keys |

The Canoe device tree embeds the ICE register window in
`ufshc@1d84000`, sets `qcom,ice-use-hwkm`, and declares the UFS, ICE, MCQ and
vendor register regions.  The active device-specific ICE implementation is the
`soc-repo` module, not the generic common-tree ICE driver.

## Current hardware-wrapped-key flow

1. F2FS supplies its `fscrypt_operations` and encrypted inode/policy state.
2. `fscrypt_select_encryption_impl()` selects inline encryption for regular
   files on an `inlinecrypt` mount and validates every filesystem block device.
3. `fscrypt_prepare_inline_crypt_key()` creates a `blk_crypto_key` with the
   policy's data-unit size and DUN width.
4. Device mapper forwards the crypto profile and wrapped-key secret operation
   to the underlying UFS block device.
5. The common UFS core attaches crypto keyslots/DUNs to UFS requests.
6. `ufshcd-crypto-qti.ko` selects HW-wrapped AES-256-XTS and calls
   `qcom_ice_program_key_hwkm()` or `qcom_ice_derive_sw_secret()`.
7. `qcom_ice.ko` uses the QTEE shared-memory bridge and `qcom-scm.ko` to invoke
   secure-world ICE services.

The generic common-tree UFS crypto profile advertises standard keys, while the
QTI module replaces it for the custom profile and advertises hardware-wrapped
keys.  Keeping the stock `.500` QTI modules and their common-kernel ABI intact
is therefore a hard boot-only requirement.

## Already integrated security work

The starting tree already contains and must not duplicate:

- CVE-2026-68147: allocation-free fscrypt device discovery, plus the OOS KABI
  adaptation that stores the new callback in an Android reserved slot.
- CVE-2026-68148: missing-superblock validation in direct-key lookup.
- CVE-2026-74595: mount-idmap-aware fscrypt policy owner check.
- CVE-2026-72103: scoped kernel credentials while device mapper opens table
  devices, including the required scoped-cleanup helpers.
- `fscrypt: Don't use problematic non-inline crypto engines`.
- 46 individually preserved F2FS integrity, corruption, memory-safety and
  lifetime fixes selected during Phase 1.

The Phase 1 candidate physically passed TWRP metadata/PIN decryption, userdata
mapper creation, F2FS `/data` mount with `inlinecrypt`, Android boot, and
existing user0 unlock.  That result is the physical oracle for every new
high-risk series.
