# ACK 6.12.40 DRM GEM framebuffer compatibility repair

## Failure evidence

The original ACK 6.12.40 boot-only candidate emitted the following warning
through the stock Qualcomm display driver:

```text
drm_gem_object_handle_put_unlocked
drm_gem_fb_destroy
drm_framebuffer_free
drm_mode_object_put
msm_ioctl_rmfb2 [msm_drm]
```

There were 13 warning headers on Android boot one and 14 on boot two.  The
initial scripted checks did not reproduce a visible display fault, but the
repository owner subsequently observed graphical errors requiring a reboot.
The original candidate is therefore a physical failure, not a harmless-warning
qualification.

## Root cause

The ACK 6.12.39 change `5f74664396ca01785f3ae13e292960ae4516cdd2`
changed `drm_gem_fb_destroy()` to release per-handle references.  The companion
generic framebuffer change that acquires those references was later reverted
for KMI, leaving the two halves inconsistent.

The Canoe Qualcomm framebuffer constructor in
`kernel_platform/vendor/qcom/opensource/display-drivers/msm/msm_fb.c` obtains
ordinary GEM object references with `drm_gem_object_lookup()`, stores them in
`fb->obj[]`, calls `drm_framebuffer_init()`, and uses
`drm_gem_fb_destroy()`.  In the incomplete ACK state, destruction attempted to
drop a handle reference that this path had never acquired.  The warning and
eventual graphical corruption are consistent with that ownership mismatch.

Android tracked the same failure as Bug 443109210 and repaired it through
Gerrit changes 3757787 and 3757788.  The first centralizes conditional handle
reference acquisition in `drm_framebuffer_init()` and release in
`drm_framebuffer_cleanup()`.  The second places the tracking flags in an
existing ABI hole in `struct drm_framebuffer`.

## Applied repair

The repair is carried as two provenance-preserving commits:

| Local commit | Official source | Purpose |
|---|---|---|
| `ffbdc861ff56c7763853c08975470ccf421a2edd` | `33c125be18de971a6b095bedd64583f62c0a51c4` | Reapply generic GEM handle-reference ownership fix |
| `ede87c5c20a785b766d818772b7972eb07e71791` | `c5058bfb5bf2e1dab569caab2f5d6ca5f072ac0e` | Place `internal_flags` in the Android KABI hole |

This is not a warning suppression and does not modify the proprietary display
module.  Framebuffers backed by user handles acquire and later release the
additional handle reference.  Internal framebuffers without handles remain
valid and do not release a nonexistent reference.

## Structural and stock-module contract

`pahole` comparison between the qualified 6.12.39 vmlinux and the repaired
6.12.40 vmlinux proves:

| Property | Qualified 6.12.39 | Repaired 6.12.40 | Result |
|---|---:|---:|---|
| `sizeof(struct drm_framebuffer)` | 192 | 192 | MATCH |
| `flags` offset | 136 | 136 | MATCH |
| KABI hole / `internal_flags` offset | unused 140-143 | 140 | ABI-safe use |
| `filp_head` offset | 144 | 144 | MATCH |
| `obj` offset | 160 | 160 | MATCH |

All affected stock `msm_drm` provider CRCs remain identical:

| Symbol | Qualified CRC | Repaired CRC |
|---|---|---|
| `drm_framebuffer_init` | `0x7492be8f` | `0x7492be8f` |
| `drm_framebuffer_lookup` | `0x51569a3f` | `0x51569a3f` |
| `drm_framebuffer_cleanup` | `0x170b9f32` | `0x170b9f32` |
| `drm_framebuffer_remove` | `0x170b9f32` | `0x170b9f32` |
| `drm_gem_fb_destroy` | `0x47e56246` | `0x47e56246` |

A complete `vmlinux.symvers` comparison between plain and repaired 6.12.40 is
empty.  No stock module, DLKM, load policy, signature policy, or protected
export changes are required.


## Payload and publication state

Stock `system_dlkm`, `vendor_dlkm`, `vendor_boot`, DTBO, VBMeta, userdata, and
metadata remain untouched.  `main` is unchanged.  No tag, push, release, or
device write was performed for this repair.
