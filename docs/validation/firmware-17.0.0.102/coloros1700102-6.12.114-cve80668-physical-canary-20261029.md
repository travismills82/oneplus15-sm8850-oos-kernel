collided with a guard helper name. The helper was renamed `image_sha`; the
corrected dry run passed. This was a host/guard compatibility correction, not
a kernel/image change. Both traces are retained.

The actual write repeated root, firmware, active-slot, boot capacity, user0,
staged candidate/rollback hashes, current qualified boot_b and inactive boot_a
guards. It wrote exactly24 blocks of4194304 bytes to `/dev/block/by-name/boot_b`

A second complete read-back was streamed to the host and compared byte-for-byte
with the frozen candidate image. Both checks matched the exact candidate SHA.
Reboot occurred only after these checks. No fastboot slot or partition metadata
was changed. The rollback remains available on the host and in the dedicated
device staging directory.

## Owner-driven mobile-data and VPN test

The owner reported “mobile is working” and said they would enable the VPN.
Android then exposed a real cellular Internet APN (cellular Internet APN network108,
rmnet_data2), distinct from the IMS network used by the initial invalid probe.
VPN client connected on tun0 and settled on network111, with network108 as its
underlying cellular transport and INTERNET/VALIDATED capabilities.

A ping explicitly bound to tun0 returned3/3 IPv4 replies, zero loss. This tests
payload through the VPN over cellular, rather than inferring cellular success
from an interface address. At~692s tun0 had704 receive/668 transmit packets
with zero interface errors/drops; conntrack was active without new diagnostics.

The initial VPN record (network110) advertised IPv6 briefly; the settled
network111 exposes onlya private IPv4 address IPv4. Actual tun0 has only link-local IPv6.
The IPv6 probe therefore does not qualify globally routed VPN IPv6 and its
failure is not proof of a kernel regression. IPv6 VPN is NOT QUALIFIED.
