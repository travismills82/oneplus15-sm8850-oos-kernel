## Warning classification and log limits

At 75.619265 s, `___slab_alloc.cold+0xbc/0x590` warned at mm/slub.c:2754,
called by `jank_hotthread_update_tick+0xa0/0x5b4` in stock
`oplus_bsp_schedinfo`, module build ID
`57d83bbf0c4904b16a651b4b7ea51db18e42889c`.
The assertion is `WARN_ON_ONCE(s->ctor && (flags & __GFP_ZERO))`.
This is not a new root: exact assertion, offsets and stock-module build ID
occur in qualified .113 boot2 at 19.646652 s and repaired .114 at 13.407044 s.
The .112 qualification already disclosed the zeroing constructor combined with
kmem_cache_zalloc. The SLUB implementation is unchanged between candidates.
No warning, detector or source behavior was suppressed to pass this test.

Other retained early warning roots (proc/sysfs registration, GIC/IRQ wake and
stock HBP fortify) match existing firmware behavior. Two firmware debug-script
SIGABRTs from failed SELinux setexeccon match the prior baseline; these are
not PID1, PIN-worker or FBE failures. They are not described as absent.
The startup advisory about unprivileged eBPF and Spectre v2 BHB is also
present, as on the prior candidate. It is an unchanged configuration/security
advisory, not a new regression or a claim of security risk elimination.

No new panic, Oops, BUG, use-after-free/refcount fault, RCU stall, lockup,
hung-task report, module-loader rejection, DRM lifetime warning or FBE/storage
failure was found in the reviewed observation captures. Early dmesg retained
only starts at 1.790509 s: messages before that may have rolled out, so an
absolute whole-boot zero-warning claim would be unsupported.
Combined saved captures extend continuously from 1.790509 through
611.399447 s. An independent review found no new warning root or
candidate-specific blocker in that retained interval.

The global GKI comparison remains FAIL/exit4 with exactly the same 38 reviewed
downstream differences. Strict KMI and the production stock-module contract
passed; there is zero new ABI delta. Neither the reference nor enforcement was
changed. Do not call this overall GKI PASS.

### Existing worker waits: scope of this test

A read-only snapshot around 527 s found the three stock-module workers in
D-state. ADCI was in `__scm_smc_call+0x220` through `si_object_do_invoke` and
`adci_fn`, not in wait_to_die. The source invokes root-object opcode8
(`adciAccept`); Qualcomm documents the supported accept invocation as one
that should not return. This is consistent with the previously documented
long-lived accept wait, not proof of a new Secure World failure or proof
that no work was pending. ZRAM was at `zram_qpace_comp+0x28`, and HFI at
`hfi_core_dbg_listener+0xb0`, matching the earlier qualified wait channels.

The existing detector uses task/wait-channel predicates, not live SCM
opcode/transaction-state inspection. That pre-existing limitation remains;
absence of a watchdog report must not be presented as independent proof
of Secure World, QPACE or HFI transaction health. No detector or worker code
was changed during the five-CVE test.
