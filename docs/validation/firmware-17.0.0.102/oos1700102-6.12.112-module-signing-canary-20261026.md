# OxygenOS 17.0.0.102 stock-module signing compatibility canary

Date: 2026-10-26

## Scope

This record covers the boot-only physical canary for the OnePlus 15
CPH2745IN running OxygenOS 17.0.0.102(EX01).  The candidate remains Linux
6.12.112, Android 16, KMI generation 6, and uses the exact stock OxygenOS 17
`system_dlkm`, `vendor_dlkm`, `vendor_boot`, `init_boot`, DTBO, and VBMeta.

## Root cause

The candidate retained the OxygenOS 16.0.10.601 trusted GKI module-signing
certificate.  OxygenOS 17 stock protected GKI modules are signed by a different
certificate.  Their source interfaces and symbol CRCs were already compatible,
but the kernel could not admit the protected modules.

The exact OxygenOS 17 certificate was extracted from the stock firmware Image
and independently matched to stock `bluetooth.ko` CMS metadata:

```text
subject: CN=Build time autogenerated kernel key
serial: 7B477824F027CBC7E584375F413360F2C0962EBC
SHA256 fingerprint: 7F:2E:5F:38:E6:27:E0:13:18:D0:E2:A3:FB:C6:60:4A:2D:75:5B:3A:AA:E4:86:F8:EC:BF:CB:10:66:2C:EC:E3
stock bluetooth.ko CMS digest: sha256
stock bluetooth.ko CMS verification with extracted certificate: PASS
```

No signature enforcement, protected-module policy, MODVERSIONS, or KMI check
was disabled.

### Watchdog and fatal-error scan

The observation window crossed both previous false-positive intervals.  At
more than 253 seconds after boot there were no reports for `adci_thread`,
`zram_comp`, or `hfi_core_dbg_cl`, and no panic, Oops, hung-task report,
soft/hard lockup, RCU stall, module signature failure, CRC disagreement,
unknown symbol, or pstore fatal record.

Two separate early-boot warnings were captured and remain driver-audit items:

1. Stock `oplus_hbp_core.ko` performs a 2048-byte copy into a source-declared
   one-byte trailing array in `hbp_frame.c:88`.  The allocation is large
   enough, but the old one-element declaration triggers the fortified
   field-spanning-write warning.  Lineage's newer source uses a flexible array;
   changing this boot-only candidate cannot alter the stock vendor-DLKM module.
2. Stock `oplus_bsp_schedinfo.ko` creates a slab cache with a zeroing
   constructor and later calls `kmem_cache_zalloc()` on it.  SLUB correctly
   warns about combining a constructor with `__GFP_ZERO`.  This is likewise in
   the unchanged stock vendor-DLKM module.

These warnings did not cause an observed functional failure, but they prevent
describing the canary as warning-clean.  They must be compared with the stock
OxygenOS 17 baseline and repaired in the matching driver/module source if a
warning-clean custom-DLKM architecture is selected; the kernel must not mask
them globally.

Status: **MODULE-SIGNING REPAIR PHYSICALLY PASSED; VENDOR-DRIVER WARNINGS REQUIRE SEPARATE AUDIT**

### Post-workload warning classification

At 943 seconds the stock OPlus power-monitor service ran the stock
`enableClkDebugSuspend` oneshot a second time.  Stock `clk_qcom` attempted to
register the same suspend trace callback again, producing `-EEXIST` and the
normal tracepoint duplicate-registration warning:

```text
tracepoint_add_func
tracepoint_probe_register
debug_suspend_write [clk_qcom]
Comm: autochmod.sh
debug_suspend_write: Failed to register suspend trace callback, ret=-17
```

This path belongs to the unchanged stock vendor-boot clock module and stock
OxygenOS power-monitor userspace.  Linux 6.12.69 already contains the same
core tracepoint duplicate-registration warning behavior, so this is not a
6.12.112 semantic change.  The correct source fix is for the clock module to
make repeated enable requests idempotent; the boot-only kernel must not weaken
global tracepoint diagnostics to conceal it.
