# Linux 6.12.80 device-mapper FBE reconciliation

## Proven regression boundary

The qualified OxygenOS 16.0.10.500 lineage previously isolated the following
two device-mapper commits as an encrypted-storage regression group:

| Linux stable commit | Subject |
|---|---|
| `e258ecf0c2a8f621ca2d08bbce6ceff4820cc762` | `dm: fix queue start/stop imbalance under suspend/load/resume races` |
| `19ca4528666990be376ac3eb6fe667b03db5324d` | `dm: fix NULL pointer dereference in __dm_suspend()` |

The complete 6.12.36 candidate without this pair passed TWRP metadata/PIN
decryption, userdata mapper creation, F2FS `inlinecrypt`, two Android boots,
and existing user0.  Linux stable first introduces the pair into the custom
post-KMI5 progression in the v6.12.52 to v6.12.53 interval, so a plain
6.12.80 candidate is not eligible for flashing.

## Compatibility design

The upstream fixes remain present and individually visible.  Request-based DM
still records `DMF_QUEUE_STOPPED`, balances queue stop/start, and does not
touch a partially initialized blk-mq queue when no live table exists.

The downstream compatibility commit changes only the mapless completion path.
Instead of skipping completion waiting entirely, it calls
`dm_wait_for_bios_completion()`.  This retains the historical bio-based
quiescence used by Android's encrypted-storage setup without consulting the
request queue or its incompletely initialized `tag_set`.

This is not a revert of either stable fix, a configuration exception, or an
ABI/KMI suppression.  TWRP existing-userdata decryption remains the decisive
runtime oracle.

## Payload scope

Only the candidate boot image may be tested.  Stock `system_dlkm`,
`vendor_dlkm`, `vendor_boot`, DTBO, VBMeta, metadata, and userdata remain
unchanged.
