# Controlled vendor_boot baseline — OOS 16.0.9.400 / slot `_b`

## Scope

This is the first vendor-boot control gate for the physically validated
`gbd70777d3d2c` matched WLAN closure.  It deliberately retains the shipping
OxygenOS vendor-ramdisk layout and changes no subsystem version, device tree,
bootconfig, init file, module list, module binary, signing policy, or AVB
parent descriptor.

The current production branch has no `kernel_platform/` source delta from the
exact matched-WLAN staging commit `eff12abc35cb12ff49ec695a9252cbe63cbbc8f8`.
The new work is limited to the audit/repack tooling and this validation record;
the physical candidate therefore remains in the already proven
`gbd70777d3d2c` kernel/module lineage.

The result is a lossless baseline repack, not a claim that every vendor-boot
module has already been rebuilt from source.  It proves the image can be
unpacked, structurally reconstructed, locally AVB-footed, and verified without
changing any byte.  Source-module replacements remain a subsequent,
independently reviewed step.

## Image and ramdisk contract

`vendor_boot_b` uses boot-image header version 4 and a 4 KiB page size.  It
contains one `vendor_ramdisk00` fragment: type `PLATFORM` (`0x1`), an empty
fragment name, and sixteen zero board IDs.  The image has a 7,560,599-byte DTB
and an unchanged bootconfig.  The b-slot vendor ramdisk is LZ4-compressed cpio
and expands to 61,068,800 bytes.

The fragment has 479 modules.  `modules.load` has 138 entries (137 distinct;
`smcinvoke` occurs twice); `modules.load.recovery` has 465 entries (464
distinct).  No charger-specific module-load list is present, so charger-mode
module policy is intentionally reported as unknown rather than inferred.

The extracted fragment contains the first-stage fstab and `lib/modules`; it
does not contain an init rc file.  The candidate therefore preserves the
shipping ramdisk's first-stage behavior, permissions, symlinks, compression,
fragment order, fragment metadata, DTB, fstab, and bootconfig.

## `mac80211` and `wonder`

The retained vendor-boot modules were explicitly evaluated because they are
potential consumers of the new matched WLAN closure.

| Module | Stock dependency declaration | Normal list | Recovery list | Exact source output | Import CRC comparison | Action |
| --- | --- | --- | --- | --- | --- | --- |
| `mac80211.ko` | `cfg80211,libarc4` | no | no | yes | 319 imports / 142 exports, all equal | retain stock dormant copy |
| `wonder.ko` | `cfg80211,mac80211` | no | no | yes | 74 imports / 0 exports, all equal | retain stock dormant copy |

Neither module is requested in a supported normal or recovery boot path.
Their raw exact-lineage build outputs have the expected `gbd70777d3d2c`
vermagic but are unsigned build artifacts, whereas the retained copies carry
the old `geb065695cf38` vermagic.  That mismatch is harmless only while the
copies remain dormant; it would be an immediate loader failure if either were
loaded under the current controlled Image.  The already deployed matching
vendor-DLKM copies are the staged, project-signed forms: both carry
`6.12.23-android16-5-o-gbd70777d3d2c-4k`, signer `Build time autogenerated
kernel key`, and `PKCS#7` signature metadata.  Their import/export CRC
comparisons pass.  Replacing dormant vendor-boot copies would nevertheless
widen the early signing and protected-provider boundary without improving the
validated normal boot.  The first candidate intentionally retains both exact
stock binaries.  A later replacement may proceed only with an explicit runtime
load path and the same full import/CRC/signature validation.

In particular, the dormant pair would consume 129 protected-provider imports
from the current matched WLAN closure: 110 from `mac80211` to `cfg80211`, 13
from `wonder` to `mac80211`, and 6 from `wonder` to `cfg80211`.  No such
consumer is allowed to load until it is part of the same signed closure.

## Signing and AVB

The matching kernel retains `CONFIG_MODULE_SIG=y`,
`CONFIG_MODULE_SIG_PROTECT=y`, `CONFIG_MODVERSIONS=y`, and
`CONFIG_GENDWARFKSYMS=y`.  Vendor-boot stock modules report no individual
module signer (`sig_id=NONE`); the existing runtime policy is preserved and no
module-security setting is changed.

The local `vendor_boot` AVB footer uses `SHA256` with algorithm `NONE` and the
stock image geometry.  Slot `_b`'s `vbmeta_b` has an
`SHA256_RSA4096` hash descriptor for the 25,190,400-byte original
`vendor_boot` payload.  The lossless candidate is byte-identical to stock
`vendor_boot_b`, so the existing `vbmeta_b` descriptor remains exactly valid.
No vbmeta image is modified.

## Candidate acceptance gates

The baseline repack verifies all of the following before an image may be
staged to slot `_b`:

1. `unpack_bootimg.py` can parse the stock image and preserves the vendor
   ramdisk fragment metadata.
2. `mkbootimg.py` reconstructs the same original payload size.
3. The stock local AVB footer geometry, salt, rollback metadata, properties,
   and unsigned local footer are reproduced.
4. `avbtool verify_image` passes.
5. Extracted DTB, bootconfig, and raw vendor ramdisk hashes match.
6. The complete image compares byte-for-byte equal to the verified stock
   b-slot backup.
7. The early normal-load dependency report has zero unresolved imports and
   zero CRC mismatches.

The candidate must be written only to `vendor_boot_b`, read back, SHA-256
verified, and then tested with the already validated `_b` boot/system-DLKM/
vendor-DLKM stack.  Any early module, storage, USB, display, or Qualcomm
platform failure requires restoration of only the verified `vendor_boot_b`
backup; slot `_a` is never touched.

## Physical validation — 2026-08-16

The lossless candidate was staged and written only to `vendor_boot_b` after a
fresh full-size backup.  Its input, staged file, block-device read-back, and
post-boot block-device SHA-256 all equal:

```text
5fe60f58ebe3f935acb3ec41585fa16977804cc0c2efd4e84c44a645a1eb7162
```

No other boot-delivery partition was rewritten for this validation.  In
particular, `boot_b`, `system_dlkm_b`, and the already validated hybrid
`vendor_dlkm_b` remained the exact `gbd70777d3d2c` matched-WLAN stack;
`vendor_boot_a` and all of slot `_a` remained untouched.  `vendor_boot` is
covered by the existing `vbmeta_b` hash descriptor, and the byte-identical
result means no AVB metadata change was required.

Two clean Android boots completed on slot `_b`.  Both reported:

```text

sys.boot_completed=1
```

## Reproduction

Run from the clean `feature/controlled-vendor-boot` worktree:

```bash
tools/repack-controlled-vendor-boot.sh \\
  --stock-image /home/travis/Android/oneplus15-controlled-vendor-boot-backup-20260816.1hXFsK/vendor_boot_b.img \\
  --out-dir out/controlled-vendor-boot
```

Then use `tools/audit-controlled-vendor-boot.py` with the exact
`gbd70777d3d2c` source-build `Module.symvers` and module output roots to
regenerate the TSV reports.  The packer refuses any non-byte-identical result;
it is not a general-purpose vendor-boot editor.
