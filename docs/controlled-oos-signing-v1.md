# Controlled OOS signing-v1 generation

This branch establishes a new, reproducible module-signing generation for the
controlled OnePlus 15 OxygenOS kernel stack. It deliberately does **not** claim
the historical `gbd70777d3d2c` signing identity: that private bundle was not
retained, so reproducing its release string with a different signer would be
incorrect.

## Trust model

The private key is deliberately outside the repository:

```text
~/.config/oneplus15-kernel/signing-v1/
├── module-signing-v1.pem        private, mode 0600
├── module-signing-v1.x509       public DER certificate
├── module-signing-v1-cert.pem   public PEM certificate
├── BUILD.bazel
└── MODULE.bazel
```

The tracked trust bundle contains exactly two public certificates:

1. the OxygenOS 16.0.9.400 stock module certificate, retained for hybrid
   stock-module compatibility; and
2. the controlled-v1 project certificate, used for every rebuilt or re-signed
   module in this generation.

The controlled-v1 certificate DER SHA-256 is
`04093d5e0b816927dc1e4fcdbd4ec754df6e69960918aa2eaa69bea6878f6faf`.

## Build

Use the guard wrapper, not a raw Bazel invocation:

```sh
tools/build-controlled-oos-signing-v1.sh --clean --all
```

It supplies the local module through Bazel's supported Bzlmod override:

```text
--override_module=oneplus15_signing=$HOME/.config/oneplus15-kernel/signing-v1
```

Without that override, the checked-in placeholder fails. There is no fallback
to Kbuild's autogenerated signing key.

The common `build_system_dlkm` helper resolves the signing key from
`CONFIG_MODULE_SIG_KEY` and the declared Kleaf output directory. This matters
for a persistent external key: Kleaf restores that declared input at the
output root under its configured basename, rather than fabricating an
undeclared `certs/signing_key.pem` copy. The helper fails if the configured
key or generated public certificate is unavailable, so the system DLKM cannot
silently be signed by another key.

The wrapper derives the SCM version from the newest committed change in the
reviewed kernel/build-input scope, writes Kleaf's supported temporary
`common/workspace_status.json`, verifies toolchain and DTS inputs, then removes
the temporary status file on exit. Documentation and package-only commits do
not change the kernel release identity. Any actual source/build-input change
does.

The resulting machine-readable release contract records the full source ID,
certificate hash, trusted-bundle hash, configuration, Module.symvers, and
artifact hashes. It is the compatibility identity for controlled-v1.

The controlled hybrid validation found 14 source replacements and 15 exact

closure. The candidate retains all 436 vendor-DLKM modules. Replacement
contract failures, unresolved imports, CRC mismatches, and active

678 compatible modules and 208 dormant modules with zero blockers.

The lossless stock vendor-boot contains 479 modules. Its normal boot list has
138 entries (137 distinct modules) and 6,351 imports; all resolve with matching
CRCs against controlled-v1. The vendor-boot copies of `mac80211` and `wonder`
remain absent from both normal and recovery load lists and must remain dormant.

`SHA256SUMS`, local AVB verification, EROFS verification, ext4 `e2fsck`, module
signer checks, and the retained-stock contract pass. The package contains no
private signing material and no VBMeta payload.

TWRP `feature/controlled-kernel-installer` commit
`571e322c7494d68f7b9fe959659a676d155cd3ad` accepts all four payloads and
enforces dependency-first ordering: vendor-DLKM, system-DLKM, vendor-boot, and
boot last. Its helper validation passes. A recovery/device dry run, verified
partition backups, read-back verification, two Android boots, and the complete
functional regression matrix are still required before this generation is
physically accepted.

## Physical result

The 2026-08-21 slot `_b` test booted controlled-v1 and validated its module
contract and 6 GHz WPA3 Wi-Fi path, but cellular data failed. A controlled A/B
rollback to r7 with the exact stock DLKM images restored LTE data immediately:
`rmnet_data3` acquired IPv4/IPv6 plus a default route, and both IP and DNS
reachability passed with zero packet loss. Controlled-v1 is therefore rejected
pending correction of its IPA/RMNET closure and must not be released or
reflashed unchanged. See
`docs/validation/controlled-oos-signing-v1-physical-2026-08-21.md`.
